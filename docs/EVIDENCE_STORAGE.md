# DPDP-COMPASS — Evidence Storage & File Security

This document explains Module 7 (Evidence Management)'s object-storage
abstraction, the local-filesystem implementation that backs it today, the
malware-scanning abstraction, the file-validation approach, and the
Vendor/Processing-Activity placeholder-reference pattern. It mirrors
`docs/SCORING.md` and `docs/RISK_METHODOLOGY.md`'s approach: an interface
resolved via DI, with one swappable implementation — so a future
deployment can move to real object storage or a real AV engine without
touching any command handler.

## 1. Why an abstraction, not PostgreSQL BLOBs

The Module 7 brief is explicit: *"Store files in object storage
abstraction. Do not store uploaded documents directly in PostgreSQL.
Database stores metadata."* `EvidenceItem` and `EvidenceVersion` hold only
metadata (title, checksum, content type, size, storage key); the file
bytes themselves live outside the database entirely, addressed by a
`StorageKey` string.

## 2. `IObjectStorageService`

`DPDP.Application.Common.Interfaces.IObjectStorageService`:

```csharp
Task UploadAsync(string key, Stream content, string contentType, CancellationToken ct = default);
Task<Stream> DownloadAsync(string key, CancellationToken ct = default);
Task DeleteAsync(string key, CancellationToken ct = default);
```

`FileSystemObjectStorageService` (`DPDP.Infrastructure.Storage`) is the
only implementation today: it writes/reads files under a configurable
root directory (`ObjectStorage:RootPath`, default `storage/evidence`,
resolved relative to the API host's working directory — see
`.gitignore`, which excludes `src/Backend/DPDP.Api/storage/` since it is
never the real storage backend in a deployed environment). Swapping to
S3/MinIO/Azure Blob later means writing one new class against this same
interface and changing the DI registration in
`DPDP.Infrastructure/DependencyInjection.cs` — no Application-layer or API
code changes.

Storage keys are generated by the upload pipeline as
`{organisationId}/{evidenceItemId}/v{versionNumber}/blob{extension}` —
tenant-scoped and collision-free by construction, so
`FileSystemObjectStorageService` never has to invent uniqueness itself.

### Path traversal defense in depth

Even though the caller always generates safe keys, `ResolveSafePath`
re-validates every key before touching the filesystem: it rejects any key
containing `..` or that resolves to an absolute path, and re-checks that
the fully resolved path still starts with the configured root. This is
deliberate defense in depth, not because a caller-supplied key is
expected — no code path ever passes user input directly as a storage key.

## 3. `IMalwareScanner`

`DPDP.Application.Common.Interfaces.IMalwareScanner`:

```csharp
public sealed record MalwareScanResult(bool IsClean, string? ThreatName);
Task<MalwareScanResult> ScanAsync(Stream content, string fileName, CancellationToken ct = default);
```

`NoOpMalwareScanner` (`DPDP.Infrastructure.Services`) always returns
`IsClean = true` and logs a `LogWarning` on every call, so the gap is
loud in logs rather than silent. Every upload still records
`EvidenceVersion.MalwareScanStatus` (`PENDING` / `CLEAN` / `INFECTED` /
`SKIPPED`) and the upload pipeline (`EvidenceFileProcessor`) already
rejects the upload with a 409 Conflict if a scanner ever reports
`IsClean = false` — that branch is unreachable with the no-op scanner but
is unit-testable directly against the command logic, and requires zero
changes when a real scanner (ClamAV, a cloud AV API, etc.) is wired in.
URL-type evidence has no file to scan and is recorded as `SKIPPED`.

## 4. File validation pipeline

Every file upload (`EvidenceFileProcessor.BuildFileVersionAsync`, shared
by both `UploadEvidenceCommand` and `UploadEvidenceVersionCommand`) runs
these checks in order, each one a distinct, independently testable layer
(`DPDP.Domain.Modules.Evidence.EvidenceFileValidator`):

1. **Extension allow-list** — only `.pdf .png .jpg .jpeg .gif .docx .xlsx
   .txt .csv .json .xml .yaml .yml` are accepted at all.
2. **Content-type-matches-extension** — the client-declared
   `Content-Type` must match the one expected extension; a `.pdf` claiming
   `image/png` is rejected even before the bytes are read.
3. **Magic-byte signature verification** — for extensions with a known
   file signature (PDF, PNG, JPEG, GIF, DOCX/XLSX's shared ZIP signature),
   the first bytes of the actual content must match. This is the layer
   that catches a renamed `malware.exe` saved as `report.pdf` with a
   forged `Content-Type` header — the two checks above only look at
   claims the client makes; this one looks at the file itself. Extensions
   with no natural magic number (`.txt .csv .json .xml .yaml .yml`) skip
   this check by design — `MatchesFileSignature` returns `true`.
4. **SHA-256 checksum** — computed server-side from the actual uploaded
   bytes (never trusted from the client) and stored on
   `EvidenceVersion.ChecksumSha256`, giving every version a
   tamper-evident fingerprint.
5. **Malware scan** — see section 3.
6. **Size limit** — enforced by `UploadEvidenceCommandValidator` against
   `EvidenceOptions:MaxUploadSizeBytes` (default 25 MB) using the file's
   declared `Length`, which FluentValidation checks *before* the handler
   ever reads the stream — an oversized file is rejected without being
   buffered into memory. `Program.cs` also caps
   `FormOptions.MultipartBodyLengthLimit` at 30 MB (25 MB + multipart
   overhead) as a transport-level backstop.

## 5. Preview safety

`EvidenceFileValidator.IsPreviewSafe` allows exactly four content types
inline: `application/pdf`, `image/png`, `image/jpeg`, `image/gif`. HTML,
SVG, and XML are deliberately excluded even though some are otherwise
harmless document formats — an inline `<iframe>`/`<img>` preview of an
attacker-controlled SVG or HTML file can execute script in the viewer's
session, so those types can only ever be downloaded, never previewed.
`DownloadEvidenceVersionQuery` has no such restriction (it's a
`Content-Disposition: attachment` download, not an inline render);
`PreviewEvidenceVersionQuery` enforces `IsPreviewSafe` and returns 409 for
anything else.

## 6. Evidence lifecycle

```
UPLOADED → UNDER_REVIEW → APPROVED → EXPIRED → ARCHIVED
                        └→ REJECTED ─────────→ ARCHIVED
```

Enforced by `EvidenceStatusTransitions` (pure, unit-tested, same pattern
as `FindingStatusTransitions`/`RemediationStatusTransitions` from Module
6). Uploading a new version always resets status to `UPLOADED` from any
non-`ARCHIVED` status, restarting the review cycle — the same
"restart, don't validate a generic transition" precedent Module 6 set for
`Finding.Reopen`. `ARCHIVED` is terminal.

Since APPROVED → EXPIRED depends on wall-clock time passing rather than a
user action, and this codebase has no background job scheduler yet,
`MarkEvidenceExpiredCommand` batch-transitions all of the caller's
organisation's overdue `APPROVED` evidence to `EXPIRED` and is exposed as
an authenticated endpoint (`POST /api/v1/evidence/mark-expired`,
`evidence.review` permission) a reviewer can trigger on demand. Wiring it
to a recurring `IHostedService`/cron job later is a drop-in change to
*what calls the command*, not a redesign of the command itself.

## 7. Separation of duties: upload vs. review

`evidence.upload` and `evidence.review` are deliberately held by
different roles in the default role templates
(`RolePermissionConfiguration`): Privacy Officer, IT Administrator, and
Department Owner hold `evidence.upload` but not `evidence.review`;
Compliance Officer and Security Officer hold `evidence.review` but not
`evidence.upload`. This is an anti-self-approval control, not an
oversight — contrast with Module 6's `FindingsCreate` permission gap
(a genuine oversight, fixed during the architecture review). The Module 7
API tests (`EvidenceApiTests.Uploader_role_cannot_review_and_reviewer_role_cannot_upload`)
assert this boundary holds in both directions.

## 8. Mapping to other entities

Per the brief, every `EvidenceItem` can be mapped to an Organisation
(always, via the standard tenant-scoping `OrganisationId`), an Assessment,
a Control, and a Finding — all real nullable foreign keys today. Vendor
and Processing Activity have no module yet, so `VendorReference` and
`ProcessingActivityReference` are free-text placeholder fields, the same
pattern Module 6 used for `Finding.AssetReference` ahead of an Asset
Inventory module. When a Vendor Management or Processing Activity Register
module ships, these become real FKs and the free-text fields are
migrated, not designed around further.

## 9. Audit logging

Every state-changing evidence action is audit-logged:
`evidence.uploaded`, `evidence.updated`, `evidence.version_uploaded`,
`evidence.submitted_for_review`, `evidence.approved`, `evidence.rejected`,
`evidence.archived`, `evidence.expired` — satisfying the brief's "Audit
every important evidence action."
